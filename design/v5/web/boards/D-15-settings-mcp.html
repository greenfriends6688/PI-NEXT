MCP 这一节要回答的是「它连上了什么、怎么连的、连上之后模型到底能调到什么」。 三件事各有一个容易翻车的地方，所以这一板把它们拆成四帧：列表里混着启用态、传输方式与认证态三种不同性质的徽章， 必须一眼分得清哪条是「连不上」哪条是「不用连」；表单是别人给你一段配置时的落点，所以入口有三条（粘贴 / 基础 / JSON）； 粘贴解析面板逐条交代「翻译了什么、丢了什么、为什么不接受」，一处理解就静默处理一处； 登录与日志分开，OAuth 过期不该藏在日志第 400 行里。

github · 环境变量来源
$GITHUB_TOKEN ← 启动 Pi 的那个 shell 的环境
从另一个终端启动 Pi Web，读到的就不是这份环境 —— 这是「令牌明明配了却 401」最常见的原因。
这一张在定什么：
  • 三种徽章是三个维度，不许合并。启用开关是要不要拉起来，传输方式（stdio / HTTP）是怎么拉， 认证态（OAuth 已登录 / 令牌过期 / 需 API Key / 不参与 OAuth）是拉起来之后能不能拿到工具。 一个 stdio 服务器照样可能要 GITHUB_TOKEN，所以「认证」不能塞进「传输」那一列。
  • 握手失败 ≠ 禁用。失败时服务器保持启用、工具从工具表撤下、配置一条不删；修好凭据后自己回到 12 个工具， 不用让用户回来再开一次开关。日志里也会明写这一点。
  • 表单三个入口不是冗余：粘贴（拿别人给的整段配置）、基础配置（不知道 JSON 的人）、 JSON 高级（args 带空格、lifecycle、toolExposure 这类键只在 JSON 里能写）。 三个入口写进同一份配置，不存在「两种形态两套解析」。
  • 粘贴解析逐条交代三类结果，不静默处理：翻译（等价改写：拆命令、降 auth 结构、 数字补成字符串）、丢弃（Pi 不读这个键，原样留在源文件里）、不接受（老式 sse:// 传输，整条不写盘）。 凡是需要猜的都进后两类。
  • 日志筛选三档而不是一个搜索框：全部 / 错误 / 握手。排查「工具能不能调」时 99% 的人要的是「错误」， 让他们先在 214 行里翻。分页固定 50 行，超期按 server 轮转，粘贴来的大响应体只留前 2KB。
  • 凭据一律不落盘：$NAME 从宿主环境读，OAuth 走系统钥匙串，面板里连「明文存进去」都做成需要解释的次要选项。
