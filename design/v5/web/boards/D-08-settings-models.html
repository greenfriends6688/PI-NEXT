推理 / 思考
档位
决定每轮请求里带不带 reasoning_effort，以及带成什么值。
不写 reasoning_effort：由供应商按这条消息的难度自己决定。延迟不可预测，但最省。
每轮带 reasoning_effort: none（本供应商的兼容开关已打开）。快，但复杂改动更容易漏。
每轮带 low。适合查资料、改文案这类不太需要绕路的活。
每轮带 medium。默认档，多数任务在这一档的性价比最好。
每轮带 high。当前默认：跨文件改动、查一个说不清的 bug 都走这一档。
每轮带 max：思考 token 也计入输出上限，慢了 3 倍，费用约为「高」的 2.4 倍。
被 enabledModels 里的 :level 钉死的档位在这一栏是只读的，面板会标「被覆盖」而不是让你改一个不生效的值。

当前 6 个
当前项目的 .pi/settings.json 覆盖了全局的 enabledModels：这里改的是项目级，全局那份不动。
这一张在定什么：
  • 模型体系是三件事，不是一张模型表。谁能被调用（供应商 + 认证）、被调用时怎么发（规格 / 推理 / Header / 兼容）、 谁负责哪种活（默认 / 命名 / 压缩）。三者混成一块列表，就没人能回答「为什么这个月花了这么多」。
  • 认证状态如实写。已登录 / 3 天后过期 / 未登录是三种不同的事实； 凭证缺失的模型不是「灰的」，而是调不动，所以提示写成「登录后即可选择」而不是画一个禁用样式。
  • 配额看供应商的账，用量看本机的账。前者是供应商认的钱（按回执），后者是本地日志的累加； 两个数字对不上是常态，面板不把它们合成一个。
  • 推理档位写清「每轮请求里多了什么」。跟随模型 = 不写 reasoning_effort；关 = 写 none； 高/最高 = 写对应值并标出延迟与倍数。被 enabledModels 的 :level 钉死的档位是只读的 —— 面板宁可标「被覆盖」，也不给一个改了不生效的下拉框。
  • enabledModels 是白名单，不是过滤器。一条都不写等于全开；写错的后果是「模型消失了」而不是「多了一个」， 所以失配条目会被诊断出来并可以一键清理，而清理只删匹配不上的那几条，不重排、不合并。
  • 思考档位的钉在 settings.json 里。面板与 pi 的 Ctrl+S 读写同一份文件，面板不抢这个位置； 项目级 .pi/settings.json 覆盖全局时，行里直接写明。
  • Header 只加到这个模型的请求里，并覆盖 Provider 的同名 Header。写全屏所有请求的 Header 会让 「为什么这个模型调不通」变成一个查两天的问题。
  • 成本档只做预估。价格来自 models.dev 的多数记录，支持数不够就标「未找到可靠价格」，不猜；账单永远以供应商回执为准。
